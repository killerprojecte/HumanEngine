# Native application composition checkpoint

This package composes native owners for integration and opt-in runtime preview.
The writable `--runtime-preview` launcher runs this graph on a test installation.
`--read-only-preview` remains read-only, and TypeScript remains the default backend.
This is not a claim of complete TypeScript Engine compatibility.

## Composed and exercised

- Installation, separate recovery authority, main SQLite database, credentials,
  pinned ICU/collation, native image codec and physical model budget service.
- HTTP settings/models, scenes, plugins, Meme, habits, Experience administration,
  diagnostics and model-call queries through their concrete stores and gates.
- Shared V1 bridge/manager host, actual adapter ingress, native model protocol,
  model-facing tool execution, delivery, disable, shutdown and restart without
  replay. No substitute JavaScript Engine or fake adapter transport is used.
- Model configuration is captured once per foreground Router/turn. An HTTP model
  update affects the next turn while accepted stages and continuations retain
  their Router. Cross-Router continuation ownership remains enforced.
- Ordinary learned advice is read only through `rules.list`, with optional
  `query`/`context` filtering. Initial preparation reads manual rules but no habit
  records. Oversized rules are withheld whole by the existing Planner byte
  budget; only delivered hints bind model-read/source identity dependencies.
  `rules_runtime_test.go` uses real SQLite/source/authority/Runtime owners and
  deterministic model calls; it is not a live-provider behavior evaluation.
  Experimental Experience policy context remains separately enabled and bounded
  to its existing three-policy selection. Background learning owners are unchanged.
- Actual semantic memory, ordinary learning, projections, working sets,
  commitments, relations and knowledge dependencies. Commitment/relation base
  schemas are initialized through their real constructors' Initialize methods.
- Model-facing `memory.search`, `memory.person` and `memory.identities`, including
  actual permission checks, original receipt identity, deferred planner selection,
  memory delivery tracking, identity state validation and scoped cached guards.
  Model-read capture is registered once by Meme; memory and identity compose
  with existing hooks rather than replacing them.
- Four additional model-facing tools: `memory.commitments`,
  `memory.commitmentTimeline`, `memory.commitmentHistory` and `memory.history`.
  Exact source descriptions, schemas, settings filters and advertisement order are
  retained. Guard capture remains current/history/timeline/historical before
  identity. Historical reads use Begin; commitment reads use GateTool.
- A genuine installed-application test proposes separate ordinary memory and
  commitment declarations, delivers original receipts through V1 model queries,
  and selects all four state tools across two plans within the source four-state
  limit. A third native send is held before transmission, answer permission is
  revoked through HTTP, and release produces no additional transmission.
  Clone/foreign/scope rejection, recall invalidation, restart/no replay and physical
  shutdown are checked. These are synthetic protocol/platform inputs, not proof of
  a live third-party platform connection.
- `memory.episodes` exposes a bounded whole qualified page without using the
  HTTP admin projection. Exact scoped experience and plan entries are checked
  at delivery, and unknown occurrence times stay unknown. Selection counts only
  retained backing assertions; this read does not grant ordinary memory parents
  or derived learning. `memory.workingSet` uses the same qualification owners and
  preserves a whole page of current accessibility and protection. A cold-only
  view can be empty with limited coverage. Pin or protection changes invalidate
  the exact read at delivery and send; recording a selection does not. Neither
  tool exposes administrator pin policies or makes accessibility a truth claim.
- Dynamic tool getters run at source operation boundaries. Runtime tests cover
  changing settings and tool availability, concurrent turns, execution-time send
  effects, first matching delivery ownership, current learning flags and current
  image extensions. Completion diagnostics do not add a sending authorization gate.
- Experience lifecycle and Planner context gate/capture, HTTP administration,
  retained source recall, same-writer invalidation and physical callback drain.
  The experimental read-only `experience.outcomes` tool exposes persisted outcomes
  for the current scene when enabled. Model-read and personalization gates apply,
  and recalled sources no longer contribute outcomes. The separately advertised
  `experience.propose` action can submit an inactive policy candidate using
  an exact outcome exposed in the current turn. Its live fixture confirms an
  existing candidate stays unchanged and no message is sent on a no-reply plan.
- The source default `learningEnabled=false` scene update is a normal successful
  HTTP path. Experience pause precedes runtime scene registration; semantic
  configuration precedes ordinary-learning, semantic, contextual and media-task
  cancellation. The application owns these effects once, avoiding duplicate epochs.
- The contextual proposal owner and keyed media-task owner handle edit, recall,
  scene cancellation and physical shutdown. Live SnowLuma inline sticker intake
  uses the media-task owner for known-only admission.
- Runtime recall runs Experience, memory, Meme and habits preparations in that
  order under the same durable source write.
- The installed proactive timer checks persisted group-scene settings and submits
  through the existing Runtime. Shutdown stops the timer before draining Runtime
  and joins accepted proactive work before closing storage.
- Async structured logs retain request/scene/turn/stage identifiers and controlled
  failure codes. Raw internal errors are not serialized into plugin events or logs.
- Startup failure cleanup, uncancelled held HTTP shutdown, accepted runtime/provider
  cleanup and database-last close are tested. A failed drain does not close borrowed
  dependencies or claim success; the application remains available for retry.

## Remaining application boundaries

- The writable launcher and packaged Compose profile are opt-in previews, not
  production cutover. A redistributable native image and production release
  acceptance remain open.
- Remaining source model tools, complete prompt/manual-rule composition and
  broader workspace behaviors remain unverified. Contextual `learning.propose` uses its
  own bounded graph. The Planner proposal action does not activate an Experience
  candidate or start a trial. The installed recall and proactive paths do not
  establish parity for all Engine startup hooks.
- Four real built-in WASM artifacts are built and required by the native test
  profile, but this graph's V1 integration does not prove all four built-ins have
  their complete product capabilities installed. Native OneBot and full SnowLuma
  transport/history/media integration remain separate work.
- Native SnowLuma live inline images can supply one first-frame description per
  turn through the native configured vision route before participation. It uses
  the exact current retained source, never learns or stores the description,
  and cannot borrow historical, managed, URL, or V1 image transport. Historical
  image transport, private media cache/fetch, and unresolved HTTP 101 behavior
  remain excluded.
- Live non-bot SnowLuma inline stickers can enter the known-only sticker
  library. Personalization and model-read must be enabled; known-only intake
  does not require scene learning. The exact retained source qualifies inside
  the existing sticker writer. When matching inline bytes already have a visible
  library analysis, Planner and Replyer can reuse its tags without a new vision
  call. With scene learning off and a configured native vision route, a fresh
  owned inline sticker can receive image-only labels without becoming included
  or shared. Identical authorized images coalesce only within the same scene;
  an exact current original must qualify at model send and label commit.
  With learning on, the retained analysis owner uses the persona and up to
  eight canonical, local text rows ending at the exact donor occurrence. It
  applies the existing automatic selection and sharing criteria; another copy
  of the image cannot replace that donor's prompt. The model dispatch and
  write require the original read permission, current source and learning mode.
  Learned expression hints are not included in this bounded background path.
  A disabling update cancels outstanding scene media work. Locator binding,
  URL or history intake, and foreground/background coalescing are excluded.
- The existing async Logger is used; complete source log retention/status/delivery
  route equivalence is not claimed. Independent read publication still preserves
  recovery checks; no constant-time cross-connection audit performance claim is made.
- Lazy security schema initialization covers SaveModels and its write-only secret
  mutations. It is not generalized to every standalone credentials/settings writer.

## Contextual learning tool composition (bounded application graph)

The application advertises the source learning.propose definition with its eight
graph/commitment/knowledge flag combinations and delegates execution to the existing
contextual proposal owner. Actual memory exposures and model-read/current-commitment
guards use the current queue writer, without retaining a write session. Historical,
identity and current freeform-learning rejection paths preserve source semantics.
Learning-only scene revocation cancels queued learning while participation-enabled
replies remain allowed; participation revocation is a separate runtime policy.

Native focused evidence covers real model selection, queued foreground admission,
ordinary proposal persistence, history/identity/current refusal, and queued learning
revocation with physical idle and zero revoked rows. This is not full learning parity:
semantic/workspace exposure domains remain uncomposed. Knowledge composition and its
separate focused evidence are described below.
Pending recall, changed-scope, typed commitment learning and concurrent-writer races
are not established by this fixture. No synthetic native replacement of guest logic
is introduced. This fixture did not exercise the writable launcher, installation
packaging/configuration or OS-signal stop. It did not change HTTP 101 or
`--read-only-preview`.

## Relation receipt and contextual entity composition

The relation model tool now uses the existing qualified relations read owner. Its
original whole linked-memory group must be delivered before exact backing refs and
a detached relation guard reach contextual learning. Validation borrows the current
read or writer authority and checks current graph flags, relation snapshots, complete
counterclaim groups and temporal applicability. It does not reopen a root publication
or retain a writer. Advertisement follows historical memory; guard capture precedes
commitment state, matching source order.

The relation fixture exercises real proposal admission, model selection, contextual
existing-entity reuse and SQL persistence; this does not establish semantic, workspace
exposure parity; knowledge has its own bounded integration below. This fixture
did not exercise native platform coverage or the writable launcher.

## Planner memory source receipts

`memory.source` accepts an alias delivered to the Planner in the current turn.
It resolves the referenced memory under the existing read authority and returns
original message IDs, not message bodies. The normal support refresh runs once;
before delivery the exact memory and source references must still match.

`TestInstalledMemorySourceTool` covers the real Planner path and rejects raw,
foreign, or earlier-turn references. It also exercises personalization policy,
and revocation by the actual admin endpoints before tool-result delivery. This
does not introduce new memory exposure or a separate final-wire source guard.

## Planner habit proposals and feedback

The Planner can submit `habits.feedback` as a plan action for a learned hint
exposed to the current turn. Only cited current live nonbot messages provide
evidence. The existing habit owner checks the scene learning policy and writes
the feedback through the same session that checks source and read authority.
If the update changes a hint already delivered to the Planner, the existing
validation invalidates the old reply plan; the separate feedback write remains.

`habits.propose` uses the existing scene rule and expression preference
writer with the exact cited live source snapshots. It does not require
personalization or memory reads; a delivered semantic, identity or knowledge
result cannot serve as authority for a free-form habit. It stays on the
foreground plan action path and does not change the queued learning pipeline.

## SnowLuma builtin installation candidate

The explicit native application graph now registers SnowLuma alongside typing-delay.
Registration does not enable a fresh builtin: credentials/configuration and the
existing Manager enablement state remain authoritative. Snow configuration,
startup credential selection, profile/history/receive decisions, media selection
and four-field original validation, send ordering and receipts execute in its
bound WASM guest. Native installation supplies transport, credentials, original
file IO and existing Engine authority owners. Disable/reconfigure logically
revoke the exact generation and physically drain its IO before WASM retirement.

The r9 app integration (session 24752) exercised real Runtime text/media dispatch,
committed receipts, original admission/removal, hot configuration, policy/runtime
unload and physical close. The same app test and linked-artifact hash/manifest test
also passed in a bwrap mount-isolated directory without application source or an
external WASM file. This proves the specified Snow installation path with explicit
Node/ICU/libvips/sqlite-vec runtime dependencies; it is not full CLI/container or
HTTP installation acceptance. The exact fresh-public composition passed its focused race/native application,
linked artifact, reproducible recipe, vet and frozen-input checks. Adapter status API wiring remains a separate batch.

Cold compilation is a known unresolved performance cost: configuration took
about 83–85s, enable 53–55s and hot configuration 56–58s. Disable completed in
milliseconds, with no policy/runtime guest retained. API closure does not claim
immediate RSS reclamation. Disk compilation-cache optimization requires a separate
owner/lifetime review and actual cold/warm measurements. Increasing the test's
setup budget does not resolve this production cost. This checkpoint did not
change the command entry point or activate a default server.


## Qualified knowledge graph composition

`memory.knowledge` uses the existing real knowledge Query/Discover owner inside the
exact runtime read authority, including the current writer for queued learning.
Its unconditional advertisement, description and schema come from the actual source.
Whole original receipts bind a detached prior-delivery chain; entity and edge authority
comes from delivered graphs, never model-supplied backing identifiers. Personalization,
current knowledge flags, exact memory-anchor guards and policy revision are checked
without opening another publication or retaining a live session. Capture follows
identity (workspace remains uncomposed), while advertisement precedes identity.

Focused native evidence exercises a real source-only Memory.Propose seed, real model
person-anchor query and whole state selection, typed existing-entity contextual learning,
and SQL-confirmed canonical declaration/edge persistence. Model aliases are restored
by the actual runtime before association with original source IDs. Learning-only
revocation permits the reply but cancels queued learning. Knowledge-answer revocation
at the physical beforeTransmit boundary suppresses sending and leaves the complete
memory/edge set unchanged; owner queues physically drain. No model prose is stored
as a substitute ordinary personal fact.

The real-owner tests additionally cover original/copy/foreign-turn receipts, delivered
entity anchors, expired/foreign read authority, same-writer uncommitted flag checks and
rollback. Source-side oracles cover fourteen receipt scenarios, but this does not claim
all have native counterparts: native reentry/out-of-order coverage and native-model
memory-anchor/Discover coverage remain separate gaps. This fixture does not cover
semantic/workspace tools, full platform validation, writable launcher and
installation packaging, or OS-signal stop. It did not change HTTP 101 or
`--read-only-preview`.
