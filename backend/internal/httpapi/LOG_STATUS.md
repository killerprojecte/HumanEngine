# Source logging delivery status

The default writable application binds `/api/logs/status` to its actual `StoreLogger` and existing `ReadPublisher`. GET and HEAD share the same authenticated route and source projection; HEAD executes the getter but sends no body. A query is ignored, the percent-encoded route is decoded, and unsupported methods/trailing paths return the source 404. This does not enable HTTP101, change default CLI/read-only behavior, or bind status for the historical raw Logger. An explicitly borrowed raw logger remains503; a borrowed Store uses its own real status without changing its ownership.

`WithLogStatus` accepts no status callback or alternate Store. It requires the server's actual Store and matching database/authority. The sole `LoggingStatus` call is inside the publisher's read callback after current recovery validation. That getter may retain a degraded notice, once per60 seconds. It is not retried after failure, cancellation or a changed publication fence, and retained notices cannot be rolled back. The complete response is copied into the existing one-entry publication response; network output and sanitized failure diagnostics run after Publish releases authority/database ownership. Failed or partial transport does not replay accepted bytes. Healthy/lazy status does not acquire leases or create directories; closed is source admission state, not a physical fd/owner exit assertion.

Request IDs are fresh UUIDv4 values even if the caller supplies one. Server-Timing uses the source recovery/handler/total names, comma spacing and two-decimal nonnegative milliseconds; random IDs and actual elapsed values are not fixed. Source authentication/readiness failures omit success headers; a throwing getter retains the authenticated handler headers. Other route families keep their existing request-ID/header behavior.
