# Actual UltraHDR source evidence and native acceptance

This is not inferred from a .jpg extension. The fixture is generated by the
installed official Sharp/libvips using sharp(raw).withGainMap().jpeg(). The
source generator asserts metadata.gainMap.image is present and nonempty. The
oracle records input SHA-256, dimensions, actual metadata format/depth and gain-map
byte count under fixtureEvidence.ultraHDR. The JPEG includes an ISO 21496-1 gain map.

The actual source oracle verifies the following generated gain-map paths:
- Original and firstFrame=true return the exact original JPEG data URL.
- 48x36 resize returns PNG and exercises no decoder pre-shrink.
- 17x13 resize returns PNG and exercises JPEG decoder pre-shrink.
The reproducible source oracle adds those paths plus a 600-byte budget/search path.
All five are part of the 52-case generator/check and passed exact native
byte/error comparison under race. The independent standalone probe also passed
all 52 cases. This evidence covers these paths, not every possible UltraHDR input.

## Exact implementation source basis

sharp/src/common.cc:308-350 includes VipsForeignLoadUhdr, UhdrFile and UhdrBuffer
in loaderToType; DetermineImageType at 354-365 maps ImageType::UHDR to JPEG.
OpenInput uses VImage::new_from_buffer with access/fail_on, but no JPEG shrink
option in its initial GetOptionsForImageType path.

sharp/src/pipeline.cc:251-265 explicitly calls VImage::jpegload_buffer with the
computed shrink only when jpegShrinkOnLoad > 1. Thus the initial UHDR auto-loader
and later forced JPEG preload are intentionally different operations.

The bridge mirrors both facts: Uhdr buffer/general loader names
map to jpeg; initial load does not add shrink=1; shrink>1 calls the public
vips_jpegload_buffer C ABI directly. The runtime library remains the same pinned
official binary. All five real gain-map cases match the actual source outputs. Do not remove
libultrahdr from a substitute build based only on ordinary JPEG tests.
