# Source transaction composition

`WithWriteSession` is separate from `Write`/`MainMutation`. It reserves main before
locking authority. Source stores join an existing session without savepoints.
Ordinary SQL/callback errors can be caught by the caller; uncaught errors roll
back main. Previously committed authority intents survive either outcome.

Reader upgrades and each intent ACK are real writes in the current main
transaction. Gate extension properties survive updates. An ACK does not prove
that the subsequent source head or subscriber effects finished. There is no
extra final authority-head check: an external append can leave a committed main
transaction behind authority, which subsequent publication rejects immediately.
This is the measured TypeScript behavior, not automatic reconciliation.

Only fixed source schema/index initialization can temporarily perform DDL.
Caller SQL cannot change schema, transactions, recovery gate, or attached files.
Callbacks run without the authority/session mutex and may synchronously invoke
other operations on the same bound store. No network work belongs here.

Native transaction loss and cancellation permanently expire the capability.
This deliberately prevents TypeScript's measured accidental autocommit after a
caught SQLite RAISE(ROLLBACK). Ordinary constraint errors do not expire it.
Retained sessions/rows cannot issue SQL after their owner callback ends. Commit
uncertainty uses the existing typed recovery CommitError; never blindly retry.

Actual-source fault evidence is generated by
`node --import tsx backend/tests/generate-source-event-recovery-fixtures.mjs`.
This boundary is not production wiring, source-witness reconciliation, or a
claim of complete bot/backend parity.

`WithWriteSession` itself is a transaction capability, not a business-readiness
assertion. Source entrypoints explicitly call AssertReady, and RecordMutation
calls RequireReader before AppendIntent. As in TypeScript `revoke`, AppendIntent
alone checks binding/transaction/expected head, not ready state or reader policy.
Closing a scoped row handle during teardown does not replay an ordinary caught
row error as a transaction-wide failure. Native transaction loss is still checked
again after row cleanup. Only currently open row handles are retained.
