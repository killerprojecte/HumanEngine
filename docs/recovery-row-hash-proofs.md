# Recovery authority validation and SQLite trust boundary

## Full verification at the boundaries that need it

Opening an authority and every explicit `entries()` audit rehash and parse the entire chain. This validates the format’s ordinary table definitions, identity count/format, sequence continuity, previous hashes, SHA-256 and event schemas. Replacing these tables with views, virtual tables or alternate conflict constraints is rejected; additional indexes do not change the format. Recovery/restore keeps these full audits. Head-only audits stream rows rather than materializing the complete chain in memory. Results contain fresh parsed objects; changing a returned head or event cannot change private validation state.

Ordinary `head()` calls reuse integrity validation of the last successfully committed SQLite snapshot. They do not scan historical rows again when SQLite reports no intervening mutation. This is integrity reuse, not permission reuse: the current main recovery gate, minimum reader capability, ready/quarantine state and authority head equality are still checked at the operation boundary. Source provenance, parent versions, deletion epochs, tombstones and post-await publication checks remain separate and current.

## Supported writes and invalidation

Validation state is private to one `RecoveryAuthority` and one SQLite connection. It is invalidated by changes to that connection's `data_version`, `total_changes()` or `schema_version`, or by a failed verification/append. External committed SQLite writes, including historical-row tampering that leaves the latest head unchanged, require a new full audit. Direct DML through the exposed connection is also detected. Change stamps are captured inside the same pinned read snapshot as verified rows, not after unlocking; a commit arriving during unlock cannot be accidentally marked verified.

Authority and gate SQL explicitly address `main` tables. Stamp reads use cached literal `PRAGMA main.data_version` and `PRAGMA main.schema_version` statements, so TEMP and virtual tables cannot impersonate mutation stamp values. These values are invalidation signals, **not cryptographic proofs of file bytes**. `data_version` observes other connections, `total_changes()` observes local DML, and `schema_version` observes schema changes. See SQLite's [data_version](https://sqlite.org/pragma.html#pragma_data_version) and [total_changes](https://sqlite.org/c3ref/total_changes.html) contracts. A caller-owned authority transaction may reuse a still-matching committed validation but cannot publish verification of its uncommitted contents. Repairing a corrupt chain inside a transaction and then rolling back therefore cannot leave a trusted repaired head behind.

An application append holds the authority's immediate transaction, validates its expected predecessor and input event, and computes the exact new row hash. It advances private validation only after the authority commit succeeds. Its mutation stamp was captured before unlocking. Durable revoke and ticket operations reject a preexisting caller-owned authority transaction before acknowledging intent in the main database; a nested savepoint is not a durable commit. The low-level append API still supports caller-owned transactions without publishing their transient validation. A later main-database rollback still leaves a durable authority/main-gate mismatch and blocks live use. The incremental path requires the exact single-row write footprint; unexpected trigger effects receive a full in-transaction audit and intended-head comparison before commit. Duplicate payload detection uses a nonunique SQLite index on `revocations(payload)`, preserving exact deduplication without a history scan per append. The old bounded per-row SHA cache is removed; private validation has constant-size retained state, not an unbounded JavaScript history cache. There are no new limits or event format changes.

The payload index is an additive authority schema change, created automatically on first open of an older installation. That first open needs write access and builds an index over existing history, requiring startup time and disk proportional to payload history. Existing installations already require writable authority storage for durable appends and constructor setup. A read-only filesystem or failed index creation fails opening rather than silently running an unindexed append path. Concurrent openers serialize index creation through SQLite. Older readers ignore the extra index; no deployment procedure or reader capability upgrade is needed.

## Fixed synchronous read units

Source batches, display, search, list qualification and recall-reference capture own a main snapshot/savepoint and authority snapshot for their fixed synchronous read implementations. They also work inside an existing main write transaction, including vector search's `BEGIN IMMEDIATE`. Both connections are query-only during this read phase. Entry validates the live gate and authority snapshot. Nested getters reuse that local result; transaction, query-only, change-counter, schema and binding invariants are checked once before the unit exits. Exceptions unwind only the owned transaction/savepoint and restore writes. After releasing the authority lock, another current gate/change check runs before the result escapes.

No transaction or read scope crosses an await. No general caller callback or reusable permission token is exposed. Main lifecycle writes and their transactional invalidation subscribers retain their existing transaction ownership. Unsupported journal configurations retain fresh ordinary checks rather than entering a snapshot scope.

## Explicitly changed unsupported-file boundary

Overwriting, replacing or restoring the raw bytes of an open SQLite authority file outside SQLite's locking/journaling protocol is unsupported. Ordinary getters no longer promise to detect such writes on every call. Stop the process before offline file maintenance, then reopen or run an explicit full audit before use. The regression using raw same-length file overwrites is retained to show that unchanged SQLite stamps do not prove byte integrity: ordinary cached reads can miss that corruption, while an explicit full audit and reopen reject it. SQLite documents these hazards under [database corruption](https://sqlite.org/howtocorrupt.html).

Manual rewinding of SQLite schema/change bookkeeping, `writable_schema` tampering and disabling the configured journaling/synchronous durability guarantees are also outside this supported operating contract. They can invalidate SQLite’s own schema, snapshot and commit guarantees; change stamps do not defend against an operator deliberately bypassing those guarantees.

This is a deliberate trust-boundary change. It does not remove startup/recovery verification or detection of writes made through supported SQLite connections, and is not a claim that stamps protect against an attacker who can arbitrarily modify live database files or process memory.
