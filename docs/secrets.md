# Stored credentials

Enter provider API keys directly in Models → Providers → API key. The same provider credential is used for text, tools, vision, embedding, and plugin-provided model operations; there is no separate mandatory environment setup. SnowLuma token fields likewise save to the database. HumanEngine does not create provider accounts or keys for you. The administrator authentication token is still required to protect the administration API.

Credentials are write-only: API reads return configuration status, never the key or ciphertext. Model `PUT /api/models` accepts a separate `credentials` map keyed by provider ID, with `{ "action": "set", "value": "..." }`, `{ "action": "preserve" }`, or `{ "action": "clear" }`. Omission preserves; empty `set` is rejected. Removing a provider removes its stored key. The UI leaves the password input empty when editing; its placeholder is not a saved value. Cancel discards edits, and clearing is explicit. Optional legacy environment references remain compatible and are never copied into the database. A stored key takes precedence; clearing it reactivates an existing legacy reference, so clear that reference too when disabling credentials entirely.

## At-rest protection and recovery

SQLite stores versioned AES-256-GCM ciphertext with random nonces and authenticated namespace/name binding. On first secret save, a random 256-bit installation key is created exclusively with mode `0600` at `.secrets.key` beside the SQLite database. It is not stored in SQLite, source control, API responses, or environment variables. The standard Docker data volume persists both database and key across restarts. Memory-only test databases use an ephemeral key. No master-key environment variable is needed.

Keep the data directory private (`0700`), protect the host and backups, and use TLS when accessing the UI remotely. Encryption protects a database-only disclosure, not an attacker who can read both the database and installation key, run code as the application user, or administer the app. Symlink keys and group/world-readable keys are rejected. Missing, malformed, or mismatched keys fail closed; HumanEngine does not silently regenerate a key for existing ciphertext. Lost installation keys make saved credentials unrecoverable: restore the matching key from a protected backup or explicitly clear/re-enter the credentials. Editing a provider key replaces its ciphertext with a fresh nonce; this is credential replacement, not installation-key rotation.

`npm run backup` copies the installation key as a separate `.secrets.key` file (0600) when the database contains secrets; restore validates and restores it. **A complete backup can decrypt credentials**, so encrypt and access-control backup storage. Never publish it or treat it as a redacted config export. A raw SQLite-only copy is insufficient for credential recovery. Preserve the existing key when relocating the database. Do not replace or rotate `.secrets.key` independently of the ciphertext.
